# PeakTalk — инструкции для агентов

## Контекст продукта

**PeakTalk** — B2C по модели покупки, но не по массовому позиционированию SaaS AI-симулятор сложных рабочих коммуникаций: защита проектов, QBR, бюджетные защиты, инвест-спичи, клиентские эскалации и другие high-stakes разговоры.

Это не consumer-продукт для «публичных выступлений вообще» и не студенческий тренажёр.  
Продуктовая суть — **stress-test аргументации до реальной встречи**, а не мотивационный speech coaching.

## Продуктовые рамки

- Сохранять narrative: B2C по модели покупки, но не массовый consumer, а scenario-driven профессиональный инструмент.
- Не уводить позиционирование в student / mass-market public speaking.
- Подчёркивать pressure testing, decision defense и сложные рабочие разговоры.
- Не инфантилизировать продукт геймификацией, «ачивками», streaks и подобной подачей.
- Если тексты и документы конфликтуют, опираться прежде всего на текущую форму кодовой базы и актуальную реализацию.

## Правила использования MCP

- Агент должен сам выбирать MCP по смыслу задачи; пользователь не обязан в каждом новом чате или промпте явно указывать нужный MCP.
- **Playwright** использовать для UI-флоу, auth-флоу, dashboard/simulation/billing проверок, регрессий, кликов по интерфейсу и браузерной верификации.
- **Sentry** использовать, когда задача связана с prod-ошибками, issue URL, replay, trace, event, stack trace или разбором инцидента.
- **Supabase** использовать, когда задача связана со схемой БД, SQL, auth, storage, таблицами, проектными настройками Supabase или проверкой данных в Supabase-контуре.
- **Figma** использовать, когда пользователь даёт Figma-ссылку или просит реализовать/сверить UI по макету.
- Если задача явно лучше решается через MCP, агенту следует использовать его проактивно, а не ждать отдельной команды вида «используй такой-то MCP».
- Если пользователь явно ограничил способ работы (например, «не ходи в браузер», «не используй Sentry», «разберись только по коду»), это ограничение важнее автоматического выбора MCP.
