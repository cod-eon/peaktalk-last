## P1: Сильные UX/продуктовые дефекты

### P1-1. Progress API endpoint typo
**Экран:** `/progress`

**Что плохо:** Эндпоинт `/simulation/progress/narrative` содержит типографскую ошибку ("narrative" вместо "narrative").

**Риск:** Пользователь может не получить данные о прогрессе, если backend ожидал корректный URL.

**Рекомендуемый фикс:** Проверить backend маршрут и переименовать в `/simulation/progress/narrative` или исправить фронт.

**Приоритет:** P1 (ломает данные, если backend не настроен под этот typo)

---

### P1-2. Typo в analysis page импорте
**Экран:** `/analysis/[id]`

**Что плохо:** Импортируется `AnimatePresence` как `AnnotatePresence` (строка 4), но в коде используется `AnimatePresence`.

**Риск:** Это работает только потому, что оба компонента экспортируются из framer-motion, но это неочевидно и может сломаться.

**Рекомендуемый фикс:** Исправить импорт на `AnimatePresence` для ясности.

**Приоритет:** P1 (клиентский баг, работает случайно)

## P2: Визуальные и архитектурные улучшения

### P2-1. Dashboard: несовпадение цветов в MetricPod
**Экран:** `/dashboard`

**Что плохо:** Функция `getScoreColor` (строки 53-54) использует цвета `#10b981`, `#fbbf24`, `#ef4444`, а `MetricPod` использует захардкожженные цвета `text-emerald-500`, `text-amber-500`, `text-red-500` в иконках.

**Риск:** Несогласованность визуальной системы — разные оттенки в разных местах.

**Рекомендуемый фикс:** Использовать `getScoreColor` для иконок в MetricPod.

**Приоритет:** P2

---

### P2-2. Meetings page: несогласованность naming
**Экран:** `/meetings`

**Что плохо:** `scenario_id` в форме встречи — это legacy-поля. По плану DL-12 привязка к сценарию должна быть через `draft_id` или `document_id`.

**Риск:** Путаница для пользователя — что выбирать: сценарий или документ?

**Рекомендуемый фикс:** Убрать поле scenario_id или переименовать для ясности. Следовать DL-12: сценарий → document/draft.

**Приоритет:** P2

---

### P2-3. Personas page: дубликат логики сложности
**Экран:** `/personas`

**Что плохо:** В карточке персоны используется `difficultyColor` функция, которая дублирует логику из setup-экрана (где сложности скрыта для кастомных персон).

**Риск:** При изменении логики нужно править в двух местах.

**Рекомендуемый фикс:** Вынести `difficultyColor` в shared constants и использовать везде.

**Приоритет:** P2

---

### P2-4. Billing page: захардкожженные условия апгрейда
**Экран:** `/billing`

**Что плохо:** Условия `canUpgradeToPlan` (строки 556-564) захардкожжены и сложны для понимания. `isPro` флаг захардкожжен.

**Риск:** При изменении тарифов будет сложно обновлять логику.

**Рекомендуемый фикс:** Вынести правила апгрейда в отдельную функцию/хелпер.

**Приоритет:** P2

## Системные паттерны проблем

### 1. Неунифицированная обработка ошибок
**Область:** Все экраны

**Что плохо:** В одних местах используется toast.error, в других — показ пустой state, в третьих — redirect.

**Риск:** Несогласованный UX при ошибках.

**Рекомендация:** Создать shared error boundary и хелпер обработки ошибок.

---

### 2. Вариативность стилей карточек
**Область:** Все экраны

**Что плохо:** Карточки (meetings, documents, personas) используют разную структуру HTML и классы.

**Риск:** Сложно поддерживать визуальную согласованность.

**Рекомендация:** Создать shared компонент Card с вариативными props.

---

### 3. Локализация date formatting
**Область:** Все экраны

**Что плохо:** Форматирование даты разбросано по компонентам (dashboard, meetings, progress, billing, report).

**Риск:** При изменении формата нужно править везде.

**Рекомендация:** Вынести `formatDate`, `formatTime`, `formatDatetime` в shared constants.

---

### 4. Mutation retry logic
**Область:** Все экраны с mutation

**Что плохо:** В одних местах `retry: false`, в других — нет настройки retry.

**Риск:** Несогласованное поведение при сетевых ошибках.

**Рекомендация:** Унифицировать retry стратегию в api client.

---
