# PeakTalk — План переработки симуляций и аудита дашборда

**Дата:** 2026-04-21
**Статус:** Design approved, ready for implementation
**Режим работы:** brainstorming handoff

---

## 1. Understanding Summary

- Исправляем критические баги в симуляциях, отчетах и переходах из встреч.
- Перепроектируем страницу настройки симуляции под новую модель с кастомными персонами.
- Разводим системных и кастомных персон на уровне UX и backend-контракта.
- Убираем недостоверные исторические данные симуляций, чтобы не тащить битые сессии и отчеты.
- Фиксируем read-only модель для шпаргалки: она создается в момент анализа и потом только читается.
- После стабилизации симуляций проводим большой визуальный и архитектурный аудит всей dashboard-зоны.

## 2. Why This Exists

- Core flow симуляций сейчас дает сбои в самых важных сценариях.
- Frontend и backend расходятся в контракте старта кастомной симуляции.
- Текущий setup-экран перестал быть логичным после добавления пользовательских персон.
- Старые данные симуляций больше нельзя считать надежными.

## 3. Scope

### Входит

- `simulation`
- `analysis`
- `meetings`
- `personas`
- `documents`
- `dashboard`
- `settings`
- `billing`
- `progress`

### Не входит

- landing
- auth
- onboarding
- guest flow
- внешние промо-страницы

## 4. Explicit Non-Goals

- Не сохранять совместимость с битым старым симуляционным контрактом.
- Не мигрировать старые недостоверные симуляции и отчеты.
- Не добавлять новый функционал вне рамок исправления потока симуляций и dashboard-аудита.
- Не делать “ленивую” догенерацию шпаргалки на странице отчета.

## 5. Assumptions

- У пользователя может быть онбординг, и его `segment` уже влияет на набор системных персон.
- `primary_goal` не должен менять состав системных персон, только рекомендации и порядок.
- Кастомная персона уже содержит свой уровень сложности через `difficulty_hint`.
- Один запуск симуляции должен использовать ровно один источник персоны: системный или кастомный.
- Исторические симуляции удалены намеренно и не подлежат восстановлению.

## 6. Non-Functional Requirements

### Performance

- Setup-экран должен открываться без дополнительных последовательных запросов сверх уже нужных данных.
- Старт симуляции не должен зависеть от второго раунда клиентских догадок о персоне.

### Reliability

- Backend должен валидировать mutually exclusive ветки старта симуляции.
- Нельзя допускать создание “зомби-сессии” с частично пустым или двусмысленным `persona_config`.

### Data Integrity

- Кастомная персона должна снапшотиться в сессию на момент старта.
- Изменение или удаление персоны после старта не должно менять уже созданные сессии и отчеты.

### Maintainability

- Один источник истины для сложности кастомной персоны.
- Один явный контракт старта для системной ветки и один для кастомной.

### UX Consistency

- Нельзя одновременно выбирать системную и кастомную персону.
- Пользователь всегда должен понимать, к какой встрече он готовится и что именно можно менять.

## 7. Decision Log

### DL-1. Исторические симуляции

**Решение:** удалить все существующие симуляции и связанные отчеты/артефакты из production.

**Альтернативы:** мигрировать; скрыть из UI; чинить частично.

**Почему выбрано:** данные уже недостоверны и мешают корректной стабилизации.

### DL-2. Экран выбора собеседника

**Решение:** модель `или-или`: либо системная персона, либо кастомная.

**Альтернативы:** кастомная плюс системная роль.

**Почему выбрано:** смешанный режим и породил двусмысленный payload и битые сессии.

### DL-3. Порядок вкладок на setup-экране

**Решение:** первой открывается вкладка `Системные`.

**Альтернативы:** первой открывать `Мои персоны`; выбирать по эвристике.

**Почему выбрано:** системный каталог остается базовым сценарием.

### DL-4. Пустое состояние пользовательских персон

**Решение:** вкладка `Мои персоны` показывается даже при нуле персон и содержит CTA `Создать персону`.

**Альтернативы:** скрывать вкладку; привязывать доступ к онбордингу.

**Почему выбрано:** пользователь должен видеть возможность, а не искать ее случайно.

### DL-5. Влияние онбординга

**Решение:** `segment` продолжает определять набор системных персон, индустрии и дефолтную сложность.

**Альтернативы:** единый каталог для всех.

**Почему выбрано:** это уже существующая бизнес-логика продукта.

### DL-6. Влияние primary_goal

**Решение:** `primary_goal` влияет только на рекомендацию и порядок системных персон.

**Альтернативы:** не использовать в UI; строить отдельный “умный” explanatory layer.

**Почему выбрано:** дает полезную персонализацию без перегрузки экрана.

### DL-7. Индустрия для кастомной персоны

**Решение:** шаг индустрии не исчезает, а предзаполняется.

**Источник предзаполнения:** встреча -> онбординг -> последнее значение -> пусто.

**Почему выбрано:** кастомная персона не заменяет контекст рынка/ниши.

### DL-8. Сложность кастомной персоны

**Решение:** отдельный шаг `Уровень давления` для кастомной персоны скрывается.

**Альтернативы:** двойной выбор сложности; склейка hint и setup-значения.

**Почему выбрано:** `difficulty_hint` уже существует в самой персоне; второй выбор только ломает UX и контракт.

### DL-9. Контракт старта кастомной симуляции

**Решение:** backend стартует кастомную симуляцию от `persona_id`, а не от собранного фронтом `persona_config`.

**Альтернативы:** гибридный контракт; фронт как источник истины.

**Почему выбрано:** только так можно убрать двусмысленность и сохранить один источник истины.

### DL-10. Снапшот кастомной персоны

**Решение:** при старте кастомной симуляции данные персоны снапшотятся в `simulation_sessions.persona_config`.

**Альтернативы:** читать живую персону из БД на каждом ходе/отчете.

**Почему выбрано:** история сессии не должна мутировать после редактирования персоны.

### DL-11. Встречи

**Решение:** на карточке встречи кнопка должна быть условной: `Подготовиться` или `Продолжить подготовку`.

**Поведение:** если уже есть активная подготовка, ведем в нее; если нет, открываем setup с предзаполнением.

### DL-12. Предзаполнение из встречи

**Решение:** связь с конкретной встречей фиксируется, но можно менять персону, индустрию и документ.

**Почему выбрано:** сохраняется сценарий подготовки именно к конкретной встрече без излишней жесткости.

### DL-13. Шпаргалка

**Решение:** шпаргалка создается один раз при создании анализа и потом только читается из БД.

**Альтернативы:** ленивое догенерирование на отчете.

**Почему выбрано:** это артефакт анализа, а не live-процесс страницы отчета.

### DL-14. Формат большого аудита

**Решение:** сначала executive summary с приоритетами, затем детальный разбор по экранам.

**Почему выбрано:** это лучший формат для управляемого исправления большого dashboard-периметра.

## 9. Final Design

### 9.1. Новый UX setup-экрана симуляции

#### Верхний контекст

- Если пользователь пришел из встречи, сверху показывается информ-блок:
  - название встречи
  - дата
  - тип встречи
  - признак того, что текущая симуляция создается именно как подготовка к этой встрече

#### Шаг 1. Выбор собеседника

- Два явных таба:
  - `Системные`
  - `Мои персоны`
- По умолчанию открыт `Системные`.
- В рамках одного запуска можно выбрать только один источник.
- При выборе системной персоны кастомная снимается.
- При выборе кастомной системная снимается.

#### Вкладка `Системные`

- Список определяется `segment` из онбординга.
- `primary_goal` используется только для:
  - сортировки
  - бейджа `Рекомендуем`
- Автовыбора не делаем.

#### Вкладка `Мои персоны`

- Показываются пользовательские персоны.
- Если их нет, показывается empty state:
  - объяснение, зачем нужны свои персоны
  - CTA `Создать персону`

#### Шаг 2. Индустрия / ниша

- Шаг виден всегда, и для системной, и для кастомной персоны.
- Значение предзаполняется по цепочке:
  - встреча
  - онбординг
  - последнее использованное значение
  - пусто
- Пользователь может менять это значение вручную.

#### Шаг 3. Контекст для тренировки

- Пользователь выбирает документ или черновик.
- Если запуск идет от встречи, факт связи со встречей сохраняется независимо от смены документа.

#### Шаг 4. Уровень давления

- Показывается только для системной персоны.
- Для кастомной персоны не показывается.
- Вместо него показывается read-only блок:
  - уровень сложности этой персоны
  - краткое пояснение, что уровень влияет на жесткость вопросов, давление и конфронтационность собеседника

---

### 9.2. Новый backend-контракт старта симуляции

#### Общий принцип

Нужно развести две ветки старта:

- системная симуляция
- кастомная симуляция

Гибридный контракт запрещен.

#### Старт системной симуляции

Frontend отправляет:

- `source_type=system`
- `persona_config.role`
- `industry`
- `difficulty`
- опционально:
  - `document_id`
  - `draft_id`
  - `meeting_id`

Backend:

- валидирует роль
- создает session snapshot для системной ветки
- стартует симуляцию

#### Старт кастомной симуляции

Frontend отправляет:

- `source_type=custom`
- `persona_id`
- `industry`
- опционально:
  - `document_id`
  - `draft_id`
  - `meeting_id`

Frontend не отправляет:

- `difficulty`
- `role`
- `communication_style`
- `focus_areas`
- `catch_phrases`
- и прочие поля кастомной персоны

Backend:

- загружает `PersonalizedPersona` по `persona_id`
- проверяет ownership
- берет `difficulty_hint` как единственный источник сложности
- собирает снапшот персоны в `simulation_sessions.persona_config`
- увеличивает `usage_count` только после успешного старта сессии

#### Содержимое session snapshot для кастомной персоны

- `source_type=custom`
- `persona_id`
- `persona_name`
- `persona_role_label`
- `industry`
- `difficulty`
- `background`
- `communication_style`
- `focus_areas`
- `catch_phrases`
- `age`
- `paid_access`
- служебные поля, нужные движку симуляции

#### Почему snapshot обязателен

- старая сессия не должна меняться после редактирования персоны
- старый отчет не должен зависеть от текущего состояния таблицы персон
- шпаргалка должна быть привязана к состоянию на момент запуска анализа

---

### 9.3. Генерация и чтение шпаргалки

#### Целевая модель

- шпаргалка создается один раз в момент анализа / завершения сессии
- шпаргалка сохраняется в БД как session artifact
- отчет ее только читает

#### Что запрещено

- повторная генерация на странице отчета
- клиентская догенерация
- “если нет, то попробуем еще раз в фоне”

#### Что это значит для UI

- если шпаргалка есть, она рендерится
- если шпаргалки нет, это считается битым состоянием данных, а не нормальным deferred flow

---

### 9.4. Карточка встречи и переход в симуляцию

#### Новая логика CTA

- `Подготовиться`, если подготовки еще нет
- `Продолжить подготовку`, если уже есть активная симуляция по этой встрече

#### Поведение

- если активная симуляция уже есть, ведем прямо в нее
- если активной симуляции нет, идем на setup-экран с предзаполнением
- связь с конкретной встречей сохраняется в любом случае

#### Редактируемость на setup-экране

Можно менять:

- персону
- индустрию
- документ / черновик

Нельзя терять:

- привязку к встрече как к целевому сценарию подготовки

---

### 9.5. Поле сложности на странице создания кастомной персоны

#### Что нужно изменить

Сейчас поле `difficulty_hint` есть, но не объясняет себя.

Нужно добавить пояснение:

- что оно влияет на жесткость вопросов
- на уровень давления
- на терпимость собеседника к расплывчатым ответам
- на интенсивность stress-test-сценария

#### Цель

Пользователь должен понимать, что задает не “декоративный уровень”, а реальное поведение собеседника.

## 10. Bug Fix Workstreams

### WS-1. Страница отчета симуляции

Исправить:

- ошибку `Не удалось экспортировать изображение`
- пропавшую шпаргалку
- работу отчета строго от сохраненных данных, а не от живой регенерации

Проверить:

- контракт `session_artifacts`
- совместимость структуры артефакта с фронтовым компонентом
- работу capture/export в реальном browser flow

### WS-2. Карточка встречи

Исправить:

- некорректную кнопку `Начать`
- ошибку `Не удалось загрузить данные встречи`
- условную логику перехода в setup или в уже существующую подготовку

### WS-3. Страница настройки симуляции

Перепроектировать:

- табы `Системные` / `Мои персоны`
- модель `или-или`
- скрытие шага давления для кастомной персоны
- правильное предзаполнение индустрии
- корректный mobile flow

### WS-4. Backend start contract

Исправить:

- поддержку `persona_id`
- проверку ownership
- сбор кастомного snapshot
- использование `difficulty_hint`
- отказ от двусмысленного payload

### WS-5. Баг “invalid choose less than 5...”

Проверить и устранить:

- любые несовпадения шкал `difficulty`
- фронтовые значения вне backend-диапазона
- любые старые клиентские пресеты, которые не маппятся в валидные значения

### WS-6. Забаганные/неконсистентные сессии

Стратегия:

- не чинить постфактум
- не скрывать
- не мигрировать
- удалять

Это уже сделано для production-истории на момент создания этого документа.

## 11. Testing Strategy

### Backend

- unit tests на обе ветки старта:
  - system
  - custom
- negative tests:
  - передан и `persona_id`, и системная роль
  - не передан ни один источник
  - чужой `persona_id`
  - отсутствующая персона
  - invalid difficulty mapping
- tests на snapshot semantics
- tests на increment `usage_count`

### Frontend

- UI logic tests на setup-экран:
  - вкладки
  - mutual exclusion
  - скрытие шага давления
  - предзаполнение индустрии
  - запуск из встречи
- regression tests на report page
- regression tests на meeting card navigation

### E2E / Manual critical paths

- системная персона -> выбор давления -> старт -> прохождение -> отчет
- кастомная персона -> без шага давления -> старт -> прохождение -> отчет
- встреча -> подготовиться -> setup -> старт
- встреча -> продолжить подготовку -> возврат в активную сессию
- отчет с существующей шпаргалкой
- экспорт карточки результата

## 14. Risks

- Старые фронтовые payload-ветки могут продолжать слать мусор после смены контракта.
- Snapshot-модель нужно внедрить аккуратно, иначе отчет и AI-слой останутся на разных структурах данных.
- Визуальная переработка setup-экрана может случайно сломать mobile flow, если не тестировать отдельно.
- Очистка истории симуляций убрала legacy-хвост, но теперь регрессии будут видны только на новых сессиях, значит нужен дисциплинированный QA.
