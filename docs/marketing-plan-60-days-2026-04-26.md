# PeakTalk — маркетинг-план на 60 дней

Дата: 2026-04-26  
Режим запуска: hybrid soft launch  
Главная цель: первые оплаты через рабочую пробную воронку  
Каналы: Threads + Telegram + Instagram-lite + SEO/linkbuilding  

---

## 1. Executive summary

PeakTalk нельзя запускать как “ещё один AI-сервис” или “тренажёр публичных выступлений”. Сильная позиция проекта:

> PeakTalk — сервис для стресс-теста аргументации перед сложной рабочей встречей.

Главная задача первых 60 дней — получить первые реальные оплаты без самообмана в метриках. Подписчики, охваты и пробные сессии важны только если они ведут к человеку, у которого скоро есть сложная рабочая встреча и понятная причина заплатить за более глубокую подготовку.

Базовая воронка:

1. Человек видит короткий острый тезис в Threads / Telegram / Instagram.
2. Узнаёт себя в конкретной ситуации: защита бюджета, roadmap, pitch, QBR, клиентская эскалация.
3. Переходит в `/simulation/guest` или на сценарную страницу.
4. Запускает пробную сессию на 3 вопроса по своему материалу.
5. Видит слабое место в аргументации.
6. Покупает разовую полную сессию за 299 ₽ или пакет 3–5 сессий, если встреч несколько.
7. Даёт feedback, который превращается в новый контент, сценарий, SEO-страницу или улучшение продукта.

Оплаты — главный критерий качества маркетинга на этом этапе. `Qualified trial starts` остаются диагностической метрикой, но не North Star: пробная сессия без payment intent может означать просто любопытство, а не рынок.

## 2. Текущее состояние по фактам

### 2.1 Что уже хорошо

- Лендинг уже сфокусирован на правильной категории: сложные рабочие встречи, аргументы, неудобные вопросы.
- Главный CTA уже понятен: “Запустить 3 вопроса бесплатно”.
- Есть публичный guest flow `/simulation/guest`.
- Есть сценарная структура: бюджет, roadmap, инвесторы, клиенты, люди, кризис.
- В `frontend/src/app/layout.tsx` уже подключена Яндекс.Метрика `108419591`.
- Есть schema.org для главной и сценариев.
- Продуктовый roadmap уже правильно смещён к “попробовать до регистрации” и pay-per-session.

### 2.2 Что обнаружено через Playwright MCP

Проверка публичного сайта `https://peaktalk.ru` через Playwright:

- Главная открывается, заголовок: “Проверьте аргументы до встречи”.
- CTA на `/simulation/guest` работает.
- Метрика грузится, Webvisor и hit-запросы уходят.
- Console на главной без ошибок.

Критичные проблемы:

1. `/simulation/guest` при запуске теста возвращает `422` на `POST /api/simulation/guest-start`.
2. `/scenarios` открывается, но показывает “Сценариев в этой категории пока нет”.
3. API `/api/scenarios` и `/api/scenarios/categories` возвращают `200`, но на публичной странице каталог фактически пуст.

### 2.3 Launch blockers

До активного трафика обязательно исправить:

| Блокер | Почему критично | Проверка |
|---|---|---|
| Guest start `422` | Главная воронка не доходит до value moment | Playwright: главная → CTA → вставить пример → начать тест |
| Пустой `/scenarios` | SEO и контент ведут в тупик | Playwright: `/scenarios` должен показывать карточки |
| Нет явных целей Метрики | Нельзя понять, какой канал работает | Проверить цели и UTM |
| Нет privacy microcopy в guest flow | Пользователь вставляет рабочий материал и может бояться | Проверить текст рядом с textarea |

Маркетинг не должен масштабироваться, пока пробная сессия не работает стабильно.

### 2.4 Карта реального продукта по текущей кодовой базе

PeakTalk уже не является только лендингом или демо-идеей. В кодовой базе есть полноценный контур подготовки:

| Зона продукта | Что уже есть | Почему важно для маркетинга |
|---|---|---|
| Публичный вход | Лендинг, `/simulation/guest`, `/scenarios`, страницы сценариев, legal pages | Можно вести человека не в абстрактный SaaS, а в конкретный stress-test |
| Guest flow | Вставка материала, выбор персоны, сложность, AI-вопросы, paywall | Это главный value moment до регистрации |
| Документы | Загрузка PDF/DOC/DOCX/TXT/MD или вставка текста | Можно продавать подготовку по реальному рабочему материалу |
| Draft-анализ | AI-анализ текста, улучшенная версия, feedback | Можно обещать не только вопросы, но и разбор слабых мест после входа в продукт |
| Симуляции | Персоны, давление, история диалога, оценка ответов | Основной платный продукт |
| Отчёты | Report page, prep-card, share-card, post-meeting feedback | Хорошая основа для платного результата после сессии |
| Сценарии | Бюджет, roadmap, инвесторы, клиенты, people, crisis | Сценарии должны стать SEO- и контентными посадочными страницами |
| Billing | Разовая сессия 299 ₽, Personal, PRO, Team, YooKassa | Для первых оплат главный оффер — разовая сессия |
| Admin | Пользователи, платежи, статистика, maintenance | Можно управлять запуском и смотреть ранние сигналы |

Формулировка для маркетинга:

> PeakTalk — не просто чат с AI. Это путь подготовки к встрече: материал → стресс-тест → неудобные вопросы → отчёт → платное продолжение.

### 2.5 Риски воронки, которые нужно явно учитывать

Эти пункты не обязательно писать пользователям, но они должны быть внутри launch-плана.

| Риск | Почему опасно | Что сделать до активного трафика |
|---|---|---|
| Guest flow обещает “3 вопроса”, но может ощущаться короче | Пользователь почувствует обман до оплаты | Проверить реальное число AI-вопросов в Playwright и backend-логике |
| Guest → paid/full session может быть хрупким | Самый горячий момент после демо теряется | Проверить путь: guest → регистрация/оплата → продолжение |
| Тарифы frontend/backend могут расходиться | Ошибки доверия и оплаты | Сверить цены, названия планов, session credits и payload billing status |
| `/blog/...` в SEO-плане ещё не реализован | Нельзя планировать публикации на несуществующие URL | До blog route использовать сценарные страницы и отдельный backlog для блога |
| Сценарные slugs в плане и коде расходятся | SEO-ссылки могут вести в 404 или не те страницы | Утвердить единую slug-карту |
| Старое позиционирование “публичные выступления” ещё встречается | Размывает категорию и привлекает не ту аудиторию | Очистить manifest, API description, метаданные, старые тексты |
| Нет явных reachGoal-событий Метрики | Нельзя понять, что привело оплату | Добавить события CTA, guest start, answer, paywall, billing, payment |

Жёсткое правило:

> Пока эти риски не закрыты, платный трафик не запускается, а органика ведётся аккуратно как ручной discovery, не как масштабирование.

## 3. Позиционирование

### 3.1 Основная формула

**PeakTalk проверяет, выдержит ли ваша аргументация давление реальной встречи.**

### 3.2 Что говорить

- “Проверьте аргументы до встречи.”
- “Получите 3 неудобных вопроса по вашему материалу.”
- “Увидьте слабые места до руководителя, клиента или инвестора.”
- “Подготовьтесь к защите бюджета, roadmap, QBR, pitch или клиентской эскалации.”
- “Не несите слабый ответ на сильную встречу.”

### 3.3 Чего не говорить

- “Научитесь красиво выступать.”
- “Прокачайте коммуникации.”
- “AI-коуч для публичных выступлений.”
- “Тренажёр soft skills.”
- “Игра / челлендж / достижения / уровни.”

### 3.4 Категория

Не “speech coaching”.  
Не “AI-чат”.  
Не “курс переговоров”.

Категория:

> AI-симулятор для стресс-теста аргументации перед рабочей встречей.

## 4. Целевая аудитория

### 4.1 Beachhead на первые 60 дней

Основатели ранних проектов + продакты / руководители направлений, которым в ближайшие 1–2 недели нужно защищать:

- бюджет;
- roadmap;
- стратегию;
- инициативу;
- pitch;
- клиентское решение;
- результаты квартала;
- последствия инцидента.

Почему они:

- часто пишут публично в Threads / Telegram;
- имеют конкретные рабочие боли;
- могут принять личное решение попробовать сервис;
- понимают цену слабой аргументации;
- дают быстрый качественный feedback.

### 4.2 Вторичные сегменты

| Сегмент | Когда подключать | Почему |
|---|---|---|
| B2B sales / account managers | после первых кейсов по клиентским эскалациям | QBR и renewal — сильная боль |
| Корпоративные менеджеры | через интро Кристины / Артура | высокая релевантность, но сложнее публично достучаться |
| Коучи / тренеры переговоров | месяц 2 | могут стать партнёрами, но не primary ICP |
| HR / L&D | месяц 3+ | ближе к B2B-продаже, длиннее цикл |

## 5. Цели и KPI на 60 дней

### 5.1 North Star на этап

**Первые оплаченные stress-test сессии** — количество людей, которые заплатили за подготовку к конкретной сложной встрече.

Диагностические метрики второго уровня:

- `qualified_trial_starts` — пробные сессии с реальным рабочим материалом;
- `guest_paywall_seen` — дошли до момента оплаты;
- `billing_opened` — открыли оплату;
- `payment_started` — начали платёж;
- `payment_succeeded` — оплатили.

Подписчики и охваты не считаются успехом сами по себе. Они полезны только если дают людей с ближайшей болезненной встречей и понятным payment intent.

### 5.2 Целевые ориентиры

| Метрика | 30 дней | 60 дней |
|---|---:|---:|
| Threads подписчики / релевантная аудитория | 200–400 | 600–1200 |
| Telegram подписчики | 50–120 | 150–300 |
| Instagram подписчики | 50–150 | 150–400 |
| Пробные сессии | 30–60 | 100–180 |
| Сессии с 2+ ответами | 15–30 | 50–90 |
| Качественные интервью / feedback | 10–15 | 25–40 |
| Успешные оплаты | 3–7 | 8–20 |
| Сильный payment intent без оплаты | 5–15 | 15–40 |
| Опубликованные SEO-страницы | 3–5 | 8–12 |

### 5.3 Weekly review

Каждую неделю фиксировать:

- топ-5 постов по переходам;
- топ-5 постов по комментариям;
- сколько людей дошли до `/simulation/guest`;
- сколько начали пробную сессию;
- где отвалились;
- какие слова повторяют пользователи в feedback;
- какие сценарии вызывают больше всего интереса;
- сколько людей дошли до paywall;
- сколько открыли billing;
- сколько начали оплату;
- сколько оплатили;
- почему не оплатили, если intent был сильный.

## 6. Канальная стратегия

## 6.1 Threads

### Роль канала

Threads — главный ежедневный канал для:

- проверки формулировок;
- роста личного бренда основателя;
- коротких острых мыслей;
- диалогов с рынком;
- отправки людей в Telegram / пробную сессию.

### Почему не звучать как бренд

Фраза “нельзя звучать как бренд” не означает, что PeakTalk должен выглядеть непрофессионально. Она означает другое: на старте нельзя говорить языком корпоративного аккаунта, где много “мы помогаем компаниям”, “наш инновационный сервис”, “подписывайтесь на обновления”. Для раннего Threads это слабый формат.

Причины:

1. **Threads — разговорная среда.** В русскоязычном сегменте лучше работают короткие наблюдения, личные выводы, вопросы, разборы ситуаций и ответы в комментариях. Сухой брендовый тон выглядит как реклама и получает меньше живых диалогов.
2. **PeakTalk продаёт доверие до ввода рабочего материала.** Человеку страшно вставлять тезисы, письма, планы встреч. Доверие быстрее возникает к основателю, который честно объясняет, что строит, что проверяет и где продукт ещё сырой.
3. **Первые оплаты требуют ручного разговора.** Брендовый аккаунт собирает “интерес”, founder-led аккаунт может написать человеку: “у тебя скоро защита бюджета? давай прогоню 3 вопроса”.
4. **Категория новая.** Люди ещё не ищут “AI stress-test аргументации”. Основатель должен объяснять рынок через конкретные рабочие боли, а не через готовую категорию.
5. **Алгоритмически важны ответы и обсуждения.** Threads продвигает посты через реакции, ответы, релевантность и свежесть обсуждения. Founder-led стиль проще провоцирует содержательные replies, чем брендовый пресс-релиз.

Правильный тон: не “личный дневник ради личного дневника”, а **основатель, который публично строит серьёзный продукт и каждый день показывает, какие слабые места в аргументации видит у рынка**.

Плохо:

```text
PeakTalk — инновационная платформа для развития коммуникативных навыков с помощью искусственного интеллекта.
```

Хорошо:

```text
Слабая защита бюджета почти всегда начинается со слов “нам нужно”.
Сильная — с ответа на вопрос: что сломается, если это урезать?
```

### Почему founder launch, а не brand launch

Для PeakTalk я выбираю founder launch не из моды на личный бренд, а из экономики первого этапа.

На старте у продукта есть три ограничения:

- категория ещё не очевидна рынку;
- доверие к вводу рабочего материала нужно создавать вручную;
- первые оплаты важнее охвата.

Brand launch лучше работает, когда категория уже понятна и есть бюджет на повторяемое продвижение. У PeakTalk пока другая задача: быстро найти 30–50 людей с реальной сложной встречей, довести часть из них до guest-flow, получить 3–7 оплат и понять, за какие сценарии реально платят.

Founder launch даёт:

- быстрые разговоры вместо абстрактных охватов;
- прямое понимание возражений;
- первые кейсы и формулировки из языка пользователей;
- возможность вручную спасать слабые места воронки;
- контент из реальных вопросов, а не из контент-плана “на воздухе”.

Ограничение: founder launch нельзя превращать в бесконечную зависимость от личности основателя. Через 60–90 дней лучшие формулировки, сценарии и ответы должны постепенно переноситься в брендовые страницы, SEO, Telegram-архив, лендинг и продуктовые onboarding-сообщения.

### Что показал ресерч русского Threads

Ресерч основан на открытых материалах и индексируемых фрагментах Threads/русскоязычных гайдов. Важно: значительная часть контента Threads плохо доступна без логина и не всегда полно индексируется, поэтому выводы нужно валидировать живым ручным мониторингом 7–10 дней.

Наблюдения:

1. **Русский Threads сейчас ближе к разговорной сети, чем к классическому B2B-медиа.** Там лучше заходят короткие мысли, спорные наблюдения, личные выводы, вопросы к аудитории и комментарии, а не длинные брендовые публикации.
2. **Много SMM/экспертного/предпринимательского контента.** Это хорошо для PeakTalk: аудитория привыкла к экспертам, личным брендам, обсуждению запусков, денег, клиентов и ошибок. Но это плохо для generic AI-постов — они быстро выглядят как шум.
3. **Охваты сами по себе обманчивы.** В русскоязычных обсуждениях часто повторяется мысль: в Threads можно получить большие просмотры, но не получить клиентов. Поэтому метрика PeakTalk — не views, а переходы в guest-flow, личные диалоги и оплаты.
4. **Лучший вход — через боль “мне скоро надо защищать решение”.** Темы “AI”, “прокачка коммуникаций”, “личная эффективность” слишком широкие. Темы “что сказать CFO”, “как отвечать инвестору”, “клиент угрожает уйти”, “roadmap режут сверху” намного конкретнее.
5. **Посты должны быть самодостаточными.** Не “читайте в Telegram”, а законченная мысль в самом Threads: ситуация → неприятный вопрос → слабый ответ → сильный ответ. CTA добавлять дозированно.
6. **Комментарии важнее частоты постинга.** Для первого месяца 20–30 содержательных комментариев в день под постами целевых людей могут дать больше, чем 5 постов в пустоту.
7. **Русскому Threads нужен человеческий конфликт, но без инфоцыганства.** Не хайп ради хайпа, а профессиональное напряжение: “вы думаете, что защищаете бюджет, но на самом деле защищаете причинно-следственную связь”.
8. **Сильная роль Telegram.** Threads лучше использовать как верх воронки и тест формулировок, Telegram — как архив доверия и место для глубоких разборов.

Источники для текущей версии выводов:

- Postium: “25+ способов продвижения в Threads в 2026 году”.
- MarketingKlub: “Продвижение в Threads. Полный гид по Тредс 2026”.
- Skillbox / Pressfeed / русскоязычные обзоры Threads: контекст по аудитории и форматам.
- Meta Help / Transparency Center: базовые правила рекомендаций и допустимого контента.
- Metricool / QuickFrame / RecurPost: публичные разборы алгоритмических факторов Threads в 2026 — replies, relevance, freshness, engagement.

| Тема | Почему подходит | Пример угла |
|---|---|---|
| Защита бюджета | Деньги, власть, конкретная боль | “Что ответить CFO, если он просит урезать 30%?” |

### Правило CTA в Threads

CTA должен быть не в каждом посте. Иначе аккаунт быстро станет рекламным.

Ритм:

- 70% — полезные острые наблюдения без ссылки;
- 20% — разборы с мягким CTA “если хотите, прогоню 3 вопроса”;
- 10% — прямой переход на PeakTalk.

Прямой CTA использовать, когда пост сам уже доказал боль:

```text
Если у вас в ближайшие 1–2 недели такая встреча — вставьте безопасный фрагмент материала и получите 3 неудобных вопроса бесплатно.
```

На странице для пользователя это обычная ссылка, но в аналитике она отвечает на вопрос: “какой канал и какая кампания привели guest-start, paywall и оплату?”

## 9. Психологические рычаги

### 9.1 Loss aversion

PLFS: +14  
Поведение: запустить пробную сессию.

Люди сильнее реагируют на риск провалить важную встречу, чем на обещание “стать лучше в коммуникации”.

Применение:

- “Слабое место лучше увидеть на экране, а не за столом переговоров.”
- “Не несите слабый ответ на сильную встречу.”

Этическая граница: не запугивать, а показывать реальный профессиональный риск.

### 9.2 Specificity

PLFS: +13  
Поведение: поверить, что продукт для конкретной ситуации.

Применение:

- не “переговоры”;
- а “защита бюджета перед CFO”;
- не “улучшить речь”;
- а “ответить на вопрос, что можно урезать без потери результата”.

### 9.3 Risk reversal

PLFS: +12  
Поведение: попробовать без страха.

Применение:

- 3 вопроса бесплатно;
- без регистрации;
- без карты;
- честно про хранение материала.

### 9.4 Authority through transparency

PLFS: +11  
Поведение: подписаться на founder-led канал.

Применение:

- публично показывать запуск;
- рассказывать, что ломается;
- показывать реальные выводы из feedback.

### 9.5 Commitment ladder

PLFS: +12  
Поведение: пройти путь от поста к пробной сессии.

Лестница:

1. Прочитал короткий пост.
2. Подписался.
3. Перешёл в Telegram.
4. Открыл сценарий.
5. Вставил безопасный пример.
6. Ответил на 1 вопрос.
7. Дошёл до 3 вопросов.
8. Оставил feedback.
9. Оплатил / вернулся позже.

## 11. MCP-протокол для реализации

### 11.1 Playwright MCP — обязательно

Использовать после любых изменений в лендинге, сценариях, guest flow, billing, аналитике.

Минимальный сценарий:

1. Открыть `https://peaktalk.ru`.
2. Проверить главный CTA.
3. Перейти на `/simulation/guest`.
4. Вставить пример.
5. Нажать “Начать тест”.
6. Получить первый вопрос без `422/500`.
7. Ответить на вопрос.
8. Дойти до paywall.
9. Проверить console errors.
10. Проверить network requests к Метрике и API.

Для маркетинга это не QA-формальность. Если Playwright показывает, что пользователь не может пройти пробную сессию, весь трафик с Threads / Telegram / SEO будет сожжён.

### 11.2 Supabase MCP

Использовать для:

- проверки таблиц, если используется Supabase DB;
- проверки storage / auth;
- проверки advisory после DDL;
- диагностики данных, если guest sessions или scenarios будут храниться в Supabase.

Важно: текущая проверка Supabase показала, что в проекте Supabase нет таблицы `public.scenarios`; значит production API, вероятно, использует другой Postgres-контур или миграции не применены в Supabase. Это нужно учитывать при диагностике.

### 11.3 Sentry MCP

Использовать после запуска трафика:

- ошибки `/api/simulation/guest-start`;
- ошибки `/api/scenarios`;
- ошибки оплаты;
- replay пользователей, которые дошли до textarea, но не стартовали;
- trace медленных AI-запросов.

### 11.4 WebSearch / FetchUrl

Использовать для:

- обновления данных по Threads / Instagram / Telegram;
- проверки новых ограничений по рекламе Meta в РФ;
- анализа SEO/GEO/AEO;
- поиска площадок для linkbuilding.

## 12. Конкретный операционный playbook

Этот раздел — не стратегия, а список действий руками. Его задача: чтобы каждое утро было понятно, что настраивать, что публиковать, что проверять и куда вести людей.

### 12.1 До запуска трафика: технический launch-gate

Сделать до активного продвижения:

1. Пройти путь `https://peaktalk.ru` → CTA → `/simulation/guest` → вставка текста → старт → первый вопрос.
2. Убедиться, что `POST /api/simulation/guest-start` не даёт `422/500`.
3. Убедиться, что пользователь реально получает обещанные 3 бесплатных вопроса или скорректировать текст обещания.
4. Проверить, что после лимита виден понятный paywall с разовой сессией 299 ₽.
5. Проверить оплату разовой сессии через YooKassa в тестовом/боевом режиме.
6. Проверить путь после оплаты: что пользователь понимает, где продолжить и что получил.
7. Проверить `/scenarios`: каталог не пустой, карточки открываются.
8. Проверить сценарные страницы: title, description, FAQ, CTA, canonical URL.
9. Сверить slugs в коде и маркетинг-плане.
10. Убрать старые формулировки “публичные выступления” из manifest, API description, metadata и видимых текстов.
11. Добавить privacy microcopy рядом с textarea: “Материал не публикуется. Не вставляйте NDA, коммерческие секреты и персональные данные; обезличьте пример, если нужно.”
12. Настроить reachGoal-события Метрики.
13. Проверить Webvisor, цели, UTM и события через Playwright/network.

```text
Попробовать 3 вопроса бесплатно: [ссылка с UTM]
```

### 12.3 Ручной мониторинг русского Threads на 7 дней

Перед тем как делать выводы по Threads, провести неделю ручного наблюдения.

Каждый день собрать в таблицу:

| Что фиксировать | Минимум в день | Зачем |
|---|---:|---|
| Аккаунты фаундеров / продактов / маркетологов / sales | 10 | Понять, где живёт целевая аудитория |
| Посты про бюджеты, клиентов, roadmap, запуск, инвесторов | 10–15 | Найти реальные формулировки боли |
| Посты с сильными replies | 5 | Понять, какой тон вызывает обсуждение |
| Комментарии с рабочими болями | 10 | Использовать язык рынка в контенте |
| Люди с ближайшей встречей / защитой решения | 1–3 | Потенциальные первые оплаты |

По итогам недели выписать:

- 20 фраз, которыми люди описывают давление;
- 10 типовых ситуаций;
- 10 возражений против PeakTalk;
- 5 тем, которые дают больше всего живых ответов;
- 3 сценария, которые стоит продвигать первыми.

Важно: не пытаться сразу “продавать всем”. Первую неделю Threads используется как разведка рынка и сбор языка, а не как рекламный канал.

### 12.4 Ежедневный workflow основателя

При 4+ часах в день:

1. 30 минут — найти 10–15 постов/обсуждений, где люди говорят о запуске, бюджете, roadmap, инвесторах, клиентах, управлении.
2. 40 минут — написать 2–4 коротких Threads-поста.
3. 45 минут — оставить 20–30 содержательных комментариев без прямого спама.
4. 45 минут — написать 5–10 личных сообщений людям с явной болью.
5. 40 минут — Telegram-пост: один разбор или один неудобный вопрос.
6. 30 минут — довести 1–3 людей до guest-flow вручную.
7. 30 минут — записать, какие слова они используют и где сомневаются.
8. 30 минут — обновить backlog контента/сценариев/SEO по фактическим вопросам рынка.

Главная ежедневная цель:

> Не “опубликовать контент”, а найти хотя бы одного человека с реальной встречей в ближайшие 1–2 недели.

### 12.5 Шаблоны постинга

#### Формат 1 — неудобный вопрос

```text
Если вы защищаете бюджет, слабое место почти всегда видно по ответу на один вопрос:

“Что конкретно сломается, если эту статью урезать на 50%?”

Если ответ: “команда не успеет” — это слабая защита.
Если ответ связывает урезание с клиентом, сроком, выручкой или риском — разговор уже другой.
```

#### Формат 2 — слабый / сильный ответ

```text
Клиент спрашивает: “Почему нам не уйти к другому подрядчику?”

Слабый ответ:
“Мы всё исправим.”

Сильный ответ:
“Вот timeline сбоя, вот что уже закрыто, вот что меняем системно, вот какой риск остаётся и как мы его контролируем.”
```

#### Формат 3 — дневник запуска

```text
Сегодня понял: люди не боятся AI-вопросов.
Они боятся вставить рабочий материал непонятно куда.

Поэтому в PeakTalk нужно говорить не “умный AI”, а:
материал не публикуется, секреты лучше обезличить, цель — проверить аргументы до встречи.
```

#### Формат 4 — прямой CTA

```text
Если у вас в ближайшие 1–2 недели защита бюджета, roadmap, pitch или сложный разговор с клиентом — могу дать 3 неудобных вопроса по вашему материалу.

Без регистрации. Без карты. Без “коучинга”.
Просто проверка слабых мест до встречи.
```

### 12.6 Личные сообщения и интро

Не писать:

```text
Привет, мы сделали AI-сервис, посмотри.
```

Писать:

```text
Привет. Увидел, что ты сейчас много пишешь про [тема]. Я делаю PeakTalk — сервис, который задаёт неудобные вопросы по рабочему материалу перед сложной встречей.

Если у тебя скоро есть защита решения / бюджет / клиентский разговор, могу бесплатно прогнать 3 вопроса по безопасному фрагменту. Мне сейчас важнее понять, где реально больно, чем что-то продать.
```

После пробной сессии:

```text
Какой вопрос был самым неприятным?
Было бы полезно получить полный stress-test с отчётом и prep-card перед реальной встречей за 299 ₽?
Если нет — чего не хватило бы, чтобы это стало очевидно полезным?
```

### 12.7 SEO/AEO действия простым языком

Сначала не писать “блог ради блога”. Делать страницы под конкретные ситуации, где человек уже чувствует давление.

Порядок:

1. Утвердить slug-карту существующих сценариев.
2. Для каждого сценария проверить title и description.
3. На каждой странице иметь первый экран с простым ответом: “что это за встреча и чем PeakTalk помогает”.
4. Добавить блок “типичные неудобные вопросы”.
5. Добавить таблицу “слабый ответ / сильный ответ”.
6. Добавить FAQ 4–6 вопросов.
7. Добавить CTA на `/simulation/guest` с UTM `scenario_page`.
8. Добавить внутренние ссылки между похожими сценариями.
9. Проверить sitemap.
10. После появления blog route — переносить лучшие Telegram-разборы в статьи.

Принцип AEO/GEO:

> Писать так, чтобы человек и AI-поисковик могли быстро вытащить ясный ответ: определение, список вопросов, конкретные примеры, FAQ, без воды.

### 12.8 Метрика и события

Минимальные цели Яндекс.Метрики:

| Цель | Событие | Где |
|---|---|---|
| CTA click | `landing_cta_clicked` | главная, nav, scenario cards |
| Guest page | `guest_page_viewed` | `/simulation/guest` |
| Guest start | `guest_started` | успешный старт сессии |
| First answer | `guest_answer_submitted` | первый ответ пользователя |
| Paywall | `guest_paywall_seen` | лимит guest-flow |
| Billing open | `billing_opened` | переход на оплату |
| Payment start | `payment_started` | создание платежа |
| Payment success | `payment_succeeded` | success page / webhook summary |

UTM должны сохраняться хотя бы в URL и аналитике:

```text
utm_source=threads / telegram / instagram / yandex / vc
utm_medium=social / owned / cpc / referral
utm_campaign=founder_launch / scenario_day / scenario_search / linkbuilding_t1
utm_content=post_slug_or_topic
```

### 12.9 Что нельзя обещать до проверки

Не обещать:

- “полная конфиденциальность”, если юридически и технически это не оформлено;
- “3 вопроса”, если фактический guest-flow даёт меньше понятных AI-вопросов;
- “PDF-отчёт”, если он недоступен на разовой сессии;
- “продолжить после демо”, пока путь guest → paid → full session не проверен;
- “готовые SEO-статьи”, пока blog route не реализован;
- “командный dashboard”, пока Team-функции не подтверждены.

Правильная формулировка на старте:

> Проверьте безопасный фрагмент материала. PeakTalk задаст неудобные вопросы и покажет слабые места аргументации до встречи.

## 16. Definition of done на 60 дней

План считается успешным, если:

- есть работающая пробная сессия без критичных ошибок;
- 600–1200 релевантных людей суммарно видят PeakTalk регулярно;
- 100+ человек дошли до пробной сессии;
- 25+ человек дали качественный feedback;
- понятны 2–3 самых сильных сценария;
- есть первые оплаты или явный payment intent;
- опубликовано 8–12 SEO/сценарных страниц;
- есть минимум 2 внешних Tier 1 материала / упоминания;
- ясно, какие каналы масштабировать в следующие 60 дней.

Если этого нет, не расширять продукт. Сначала чинить сообщение, воронку и сценарии.
